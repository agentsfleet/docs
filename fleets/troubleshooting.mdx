# Troubleshoot a fleet

## Symptom

| Symptom | First check |
|---|---|
| Every command fails | Run `agentsfleet doctor`. |
| A webhook does not create a run | Read recent webhook events. |
| A connected GitHub App sends nothing | Check `repositories` in the fleet's Definition. |
| A run starts and fails | Read the activity stream error. |
| A fleet returns the wrong result | Compare tool calls with the fleet's instructions. |
| New runs are blocked | Check fleet state and budgets. |
| Files from the last message are gone | Read [What a follow-up message keeps](/fleets/overview#what-a-follow-up-message-keeps). |

## Why it happened

Most failures come from authentication, workspace selection, webhook signatures, missing secrets, tool access, or budget limits.

Every API error carries a stable error identifier and request identifier. Use both values when comparing a response with the error registry.

## How to fix it

1. Check client and workspace health.

   ```bash
   agentsfleet doctor
   ```

   ```text
   <varies>
   ```

2. Read the fleet's recent errors.

   `<FLEET_ID>` comes from `agentsfleet list`.

   ```bash
   agentsfleet events <FLEET_ID> --since 1h --json
   ```

   ```text
   <varies>
   ```

   In the dashboard, open the failed event and click **Copy diagnostic**.
   The copy contains its event identifier, failure class, and recorded cause.
   For a reply that stopped early, it also carries safe stream counters when
   the runner reported them.

   Share that copy with an operator; the event
   identifier lets them find the run across multiple runners.

3. Apply the fix named by the stable error identifier.

   `UZ-REQ-001` from a chat or Save points to an invalid Definition field. A Save that stays `installing` names each missing secret or grant.

   `UZ-WH-010` points to a signature mismatch. `UZ-AGT-012` points to a fleet that cannot accept work.

4. When a connected GitHub App sends nothing, check the subscription.

   An App delivery reaches every fleet in the workspace, so each fleet says
   which repositories it wants. A fleet that names none subscribes to none.

   Open the delivery in **GitHub → Settings → Integrations → the App → Recent
   Deliveries**. A body of `{"ignored": "UZ-WH-022"}` under a `200` means the
   event arrived and matched no fleet. The status is green either way, so read
   the body.

   Then check two things. The fleet's webhook trigger needs `repositories` beside
   `"source": "github"`, spelled `owner/repository`; case does not matter. And the
   fleet needs an approved integration grant.

   ```bash
   agentsfleet grant list --fleet <FLEET_ID>
   ```

   ```text
   <varies>
   ```

5. Retry the original event once.

   Lifecycle commands send a write again only when the connection was refused or the server declined to run it. A reset after sending or a timeout surfaces the error. Provider webhooks follow the provider's own retry policy.

## How to prevent it

Run `agentsfleet doctor` before installation. Test one manual message before registering a webhook.

Keep the fleet's instruction steps numbered, and name only tools its Definition declares. Store stable provider event identifiers for duplicate protection.

Use fleet budgets to bound cost. Check the activity stream after every applied setup change.
