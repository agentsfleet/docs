## What it is

A tool gives a fleet one named action. The runtime determines which tools a run can call.

| Group | Tools |
|---|---|
| Network and notifications | `http_request`, `web_fetch`, `web_search`, `notify` |
| Memory | `memory_store`, `memory_recall`, `memory_list`, `memory_forget` |
| Access and questions | `request_access`, `ask_user` |
| Triggers and schedules | `trigger_add`, `trigger_list`, `trigger_remove`, `schedule`, `cron_add`, `cron_list`, `cron_remove`, `cron_update`, `cron_run`, `cron_runs` |
| Work and messages | `task_start`, `task_input`, `propose_change`, `update_plan`, `message`, `fleet_activity`, `fleet_steer` |
| Delegation | `delegate`, `spawn`, `wait_agent`, `send_input`, `list_agents`, `interrupt_agent` |
| Files and local work | `file_read`, `file_write`, `file_edit`, `apply_patch`, `shell`, `exec_command`, `write_stdin`, `git`, `image` |

`exec_command` starts a process the fleet can drive across calls. `write_stdin` sends input to that process. `apply_patch` changes files in the sandbox workspace.

## Why it exists

The allowlist limits what the fleet can do. The fleet's instructions do not grant access by themselves.

## How it behaves

The runtime enforces the run's tool and network policy. A call outside that policy returns a tool error.

A tool such as `http_request`, `git`, or `notify` can need an approved credential. The fleet uses `request_access` to ask, and a person decides the access card in chat.

The runner operator's policy controls what sandbox processes can reach. The fleet's HTTP switches govern its HTTP tools.

### Command endings

`shell` and `git` accept `timeout_ms`, with a ten-second default and a ten-minute maximum.
A confirmed process timeout returns `timed_out`.

<Note>This feature is coming soon.</Note>

The runner also bounds its wait for the command's ending, allowing five extra seconds for cleanup and output delivery.
If no ending arrives, the tool returns `interrupted` with available output and closes its sandbox connection.
Later calls on that connection fail promptly.

The command's outcome remains unknown; inspect its effects before asking the fleet to repeat it.

### HTTP egress settings

A fleet starts with **Allow all** and **Packages** off. Open its chat to change these switches.

| Control | Effect |
|---|---|
| **Allow all** | Allows HTTP tools to reach public destinations. Private addresses still fail the network check. |
| **Packages** | Allows the standard npm, Python, Rust, and Go package registries. |

The terminal command is `agentsfleet fleet network use <FLEET_ID> <allow-all|private>`. Add `--packages` or `--no-packages` to change the package setting. You can address a fleet as `@NAME`.

The API accepts `http_egress` and `package_domains` on the fleet update route. Include the fleet's current `ETag` in `If-Match`.

### Schedule tools

A fleet can plan its own follow-up runs. `agentsfleet` keeps every schedule and fires it; the runner keeps no timer.

| Tool | What it does |
|---|---|
| `cron_add` | Creates a recurring schedule from a five-field cron expression, a message, and an optional zone. The zone defaults to Coordinated Universal Time (UTC). |
| `schedule` | Creates one follow-up at a moment within the next year. The moment rounds up to the next whole minute, which must be at least a minute away. The schedule runs once and is then removed; running it with `cron_run` counts as that one run. |
| `cron_list` | Lists every schedule of the fleet. |
| `cron_update` | Changes, pauses, or resumes a schedule the fleet created. |
| `cron_remove` | Deletes a schedule the fleet created. |
| `cron_run` | Runs a schedule now. The new run waits behind the current one. A run that a schedule started cannot run a schedule now. |
| `cron_runs` | Lists a schedule's runs, newest first, 50 at a time. A `schedule` follow-up's run stays listed after the follow-up is removed. |

A schedule the fleet creates appears beside your own on the fleet's schedules list, with source `fleet`. You can change or delete it there like any other schedule.

<Note>This feature is coming soon.</Note>

Schedule changes, registration results and fire messages also appear in [fleet chat](/fleets/running#read-schedule-activity).
Once a fired run starts, choose **Run details** beside its activity to inspect its recorded result.

`agentsfleet` replaces any value from the fleet's secrets with `«secret:NAME»` in a schedule's message before it saves the schedule. A `schedule` follow-up is removed without running if the fleet is inactive when it is due. The same happens if `agentsfleet` could not register it before its moment.

### Message tool

`message` posts one line to the Slack thread that started the run, before the run answers. Use it for progress, such as "fix pushed, re-checking at 09:00".

`agentsfleet` posts the line with the workspace's Slack connection. The fleet never holds the Slack token. `agentsfleet` replaces any value from the fleet's secrets with `«secret:NAME»` before it posts.

Apart from those replaced secrets, the line appears as plain text, as the fleet wrote it. A `<!channel>`, `<!here>`, or user mention in it shows as text and notifies nobody.

### Child agents

A child agent is a second agent inside the same run, working on one task. It shares the run's sandbox, files, and memory. It starts from its task alone and does not see the conversation.

A child holds the tools named in the call's `tools` list, and its parent must hold each one. Without `tools`, the child holds every tool its parent holds. Naming a tool the parent lacks answers `child_tool_not_held`.

| Tool | What it does |
|---|---|
| `delegate` | Starts a child on `task` and waits for its answer, which becomes the call's result. A failed child answers `child_failed`, and an interrupted one answers `interrupted`. |
| `spawn` | Starts a child on `task` that works alongside the fleet, and answers its `child_id` at once. |
| `wait_agent` | Waits for a spawned child to end, then answers its status and its answer. `timeout_ms` defaults to 30,000 milliseconds and is capped at 3,600,000 (one hour). A child still working when the wait ends reads `running`, and `0` checks without waiting. |
| `send_input` | Queues `message` for a spawned child's next turn and answers whether the child accepted it. A child that has ended accepts nothing. |
| `list_agents` | Lists every child of the run with its `child_id`, status, depth, and number of tool calls. |
| `interrupt_agent` | Stops a spawned child where it is. Its open tool call and the child both end `interrupted`. |

A child's status is `running`, `done`, `failed`, or `interrupted`. A `child_id` this run never issued answers `child_not_found`.

## Limits

`http_request` accepts only hosts allowed by the fleet policy. Responses allow up to 1 MiB.

<Note>
  This feature is coming soon. A `GET` without a body follows up to three redirects.

  Every destination must pass the fleet's existing network and request rules. Other methods and requests with a body return the first response.
</Note>

A redirect must pass the same HTTP policy as the original request.

All supplied headers are removed permanently when the origin changes, including when a later redirect returns to the original origin.

The whole redirected read has a 30-second deadline. Intermediate bodies are discarded.

After a redirect, the final response shows its status and redirect count.
A returned content type appears before the body.
Temporary download paths and signatures stay private under the tool's known-target masking rules.

Truncation and replaced non-UTF-8 bytes appear before the response body. If your task requires complete text, instruct the fleet to stop when it sees either notice or an unusable content type. For a Continuous Integration (CI) investigation, require the exact run attempt, job metadata and usable log text before diagnosing the failure.

`browser`, `browser_open` and `screenshot` are currently unavailable on every runner.
Use `http_request` or `web_fetch` for HTTP reads.

`web_fetch` requires an allowed public secure HTTP (HTTPS) destination. Private or unsafe destinations are refused.

Child agents nest two levels deep. A child can start children of its own. Those grandchildren are offered none of the six child-agent tools.

A run has at most 4 children working at once and starts at most 16 in all. Past either cap, `delegate` and `spawn` answer `child_cap_reached`.

When the run ends, every child still working ends `interrupted`.

To revoke a credential, remove it from **Can access**. Later runs and token requests use the updated access.

A fleet can hold 32 schedules in total, including up to 16 it creates itself.
A 17th fleet-created schedule fails with [`UZ-SCHED-009`](/api-reference/error-codes#UZ-SCHED-009).
Changing or deleting a schedule a person created fails with [`UZ-SCHED-010`](/api-reference/error-codes#UZ-SCHED-010).

`cron_run` fails with [`UZ-SCHED-011`](/api-reference/error-codes#UZ-SCHED-011) for a paused schedule, a schedule being removed, or a run that a schedule started. It fails with [`UZ-AGT-012`](/api-reference/error-codes#UZ-AGT-012) while the fleet is not active.

`message` posts at most 8 lines per run, each at most 4,096 bytes. The 9th line fails with [`UZ-RUN-020`](/api-reference/error-codes#UZ-RUN-020). A run started from the API, a webhook, or a schedule has no thread, so `message` fails with [`UZ-RUN-019`](/api-reference/error-codes#UZ-RUN-019).

If Slack refuses a line, or has not taken it within 12 seconds, `message` reports the line as not delivered.
The run continues; final-answer delivery follows its own retries and can also fail.
