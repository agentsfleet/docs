# Fleet tools

## What it is

A tool gives a fleet one named action. The fleet author declares allowed tools in `TRIGGER.md`.

| Group | Tools |
|---|---|
| Network | `http_request`, `web_search`, `web_fetch`, `pushover` |
| Memory | `memory_store`, `memory_recall`, `memory_list`, `memory_forget` |
| Schedule | `cron_add`, `cron_list`, `cron_remove`, `cron_update`, `cron_run`, `cron_runs`, `schedule` |
| Delegation | `delegate`, `spawn`, `wait_agent`, `send_input`, `list_agents`, `interrupt_agent` |
| Files | `file_read`, `file_write`, `file_append`, `file_delete`, `file_edit`, `file_read_hashed`, `file_edit_hashed` |
| Local work | `shell`, `git`, `calculator`, `image` |
| Browser | `browser`, `browser_open`, `screenshot` |
| Messaging | `message` |

## Why it exists

The allowlist limits what the fleet can do. Instructions in `SKILL.md` do not grant access by themselves.

## How it behaves

The runtime owns the built-in tools. A fleet receives only names listed under `x-agentsfleet.tools`.

```yaml
x-agentsfleet:
  tools:
    - http_request
    - memory_recall
  network:
    allow:
      - api.github.com
```

`http_request` also follows the network host list. Secret references are filled by the credential firewall during an approved outbound request.

An unknown tool is skipped and records `UZ-TOOL-005` in the activity stream. The run continues with the remaining valid tools.

### Schedule tools

A fleet can plan its own follow-up runs. `agentsfleet` keeps every schedule and fires it; the runner keeps no timer.

| Tool | What it does |
|---|---|
| `cron_add` | Creates a recurring schedule from a five-field cron expression, a message, and an optional zone. The zone defaults to Coordinated Universal Time (UTC). |
| `schedule` | Creates one follow-up at a moment within the next year. The moment rounds up to the next whole minute, which must be at least a minute away. The schedule runs once and is then removed; running it with `cron_run` counts as that one run. |
| `cron_list` | Lists every schedule of the fleet. Each one names its source: `fleet`, `api` for a person, or `trigger` for `TRIGGER.md`. |
| `cron_update` | Changes, pauses, or resumes a schedule the fleet created. |
| `cron_remove` | Deletes a schedule the fleet created. |
| `cron_run` | Runs a schedule now. The new run waits behind the current one. A run that a schedule started cannot run a schedule now. |
| `cron_runs` | Lists a schedule's runs, newest first, 50 at a time. A `schedule` follow-up's run stays listed after the follow-up is removed. |

A schedule the fleet creates appears beside your own on the fleet's schedules list, with source `fleet`. You can change or delete it there like any other schedule.

`agentsfleet` replaces any value from the fleet's secrets with `«secret:NAME»` in a schedule's message before it saves the schedule. If the fleet is paused when a `schedule` follow-up is due, or `agentsfleet` could not register the follow-up before its moment, the follow-up is removed without running.

### Message tool

`message` posts one line to the Slack thread that started the run, before the run answers. Use it for progress, such as "fix pushed, re-checking at 09:00".

`agentsfleet` posts the line with the workspace's Slack connection. The fleet never holds the Slack token. `agentsfleet` replaces any value from the fleet's secrets with `«secret:NAME»` before it posts.

Apart from those replaced secrets, the line appears as plain text, as the fleet wrote it. A `<!channel>`, `<!here>`, or user mention in it shows as text and notifies nobody.

### Child agents

<Note>The child-agent tools run on the Rust runner, which replaces the current runner at the cutover.</Note>

A child agent is a second agent inside the same run, working on one task. It shares the run's sandbox, files, memory, and budget. It starts from its task alone and does not see the conversation.

A child holds the tools named in the call's `tools` list, and its parent must hold each one. Without `tools`, the child holds every tool its parent holds. Naming a tool the parent lacks answers `child_tool_not_held`.

| Tool | What it does |
|---|---|
| `delegate` | Starts a child on `task` and waits for its answer, which becomes the call's result. A failed child answers `child_failed`, and an interrupted one answers `interrupted`. |
| `spawn` | Starts a child on `task` that works alongside the fleet, and answers its `child_id` at once. |
| `wait_agent` | Waits for a spawned child to end, then answers its status and its answer. `timeout_ms` defaults to 30,000 milliseconds and is capped at 3,600,000 (one hour). A child still working when the wait ends reads `running`, and `0` checks without waiting. |
| `send_input` | Queues `message` for a spawned child's next turn and answers whether the child accepted it. A child that has ended accepts nothing. |
| `list_agents` | Lists every child of the run with its `child_id`, status, depth, and number of tool calls. |
| `interrupt_agent` | Stops a spawned child where it is. Its open tool call and the child both end `interrupted`. |

A child's status is `running`, `done`, `failed`, or `interrupted`. A `child_id` this run never issued answers `child_not_found`.

## Limits

`http_request` accepts only hosts allowed by the fleet policy. Responses allow up to 1 MiB.

Hosted runners have no display. `browser_open` and `screenshot` can fail there; use them only with a suitable self-managed runner.

`web_fetch` does not use the fleet host list. Use `http_request` when a host restriction is required.

Child agents nest two levels deep. A child can start children of its own. Those grandchildren are offered none of the six child-agent tools.

A run has at most 4 children working at once and starts at most 16 in all. Past either cap, `delegate` and `spawn` answer `child_cap_reached`.

When the run ends, every child still working ends `interrupted`.

Remove a tool name from `TRIGGER.md` to revoke it. The next fleet update applies the new list to later runs.

A fleet creates at most 16 schedules itself, inside the 32 a fleet holds. The 17th fails with [`UZ-SCHED-009`](/api-reference/error-codes#UZ-SCHED-009). Changing or deleting a schedule a person created fails with [`UZ-SCHED-010`](/api-reference/error-codes#UZ-SCHED-010).

`cron_run` fails with [`UZ-SCHED-011`](/api-reference/error-codes#UZ-SCHED-011) for a paused schedule, a schedule being removed, or a run that a schedule started. It fails with [`UZ-AGT-012`](/api-reference/error-codes#UZ-AGT-012) while the fleet is paused.

`message` posts at most 8 lines per run, each at most 4,096 bytes. The 9th line fails with [`UZ-RUN-020`](/api-reference/error-codes#UZ-RUN-020). A run started from the API, a webhook, or a schedule has no thread, so `message` fails with [`UZ-RUN-019`](/api-reference/error-codes#UZ-RUN-019).

If Slack refuses a line, or has not taken it within 12 seconds, `message` reports the line as not delivered. The run continues, and its answer still reaches the thread.
