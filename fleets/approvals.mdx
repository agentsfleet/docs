# Approve a waiting run

## What this does

Some fleets ask for access that a person has to grant. A run that asks parks at an approval gate until someone decides it.

`agentsfleet approvals` lists those gates, shows what one grants, and records the decision from your terminal.

## Before you begin

Install a fleet that opens gates. Two kinds reach the inbox:

| Kind | Raised by | Scope of a decision |
|------|-----------|---------------------|
| `integration_grant` | a mintable credential a fleet declares after install, or a fleet installed before grants were answered at install | Holds until somebody revokes the grant. |
| a kind you name | a rule you write under `gates:` in `TRIGGER.md` | Whatever that rule's `blast_radius` says. |

Installing a fleet that declares a mintable credential answers its grant then
and there. You chose the fleet, its bundle names the integration, and
`TRIGGER.md` names the repositories. No card is raised.

The `github-pr-reviewer` bundle installs and reviews without asking you
anything.

A repository write is covered by that grant. Fleets used to raise a
`repository_write` gate on every run, and no longer do.

Sign in and select the workspace that owns the fleet. A tenant API key needs `approval:read` to list gates and `approval:resolve` to decide them.

## Steps

1. List the gates waiting in the active workspace.

   ```bash
   agentsfleet approvals list
   ```

   ```text
   GATE      FLEET     KIND      STATUS    ACTION
   <varies>  <varies>  <varies>  <varies>  <varies>
   ```

   Add `--fleet <FLEET_ID>` to narrow the list to one fleet.

2. Read what the gate grants.

   `<GATE_ID>` comes from the `GATE` column.

   ```bash
   agentsfleet approvals show <GATE_ID>
   ```

   ```text
   <varies>
   ```

   The block names the fleet, the gate kind, its status, and the blast radius. The blast radius is one sentence naming what an approval reaches.

3. Decide the gate.

   ```bash
   agentsfleet approvals approve <GATE_ID>
   ```

   ```text
   <varies>
   ```

   Deny it instead when the reach is wider than the work needs.

   ```bash
   agentsfleet approvals deny <GATE_ID>
   ```

   ```text
   <varies>
   ```

## Verify it works

```bash
agentsfleet status
```

```text
Fleets
Name: <varies>
Status: active
Events: <varies>
Budget: <varies>
Waiting: 0
```

`Waiting` counts the gates the fleet is parked on. An approved run continues where it stopped, and `agentsfleet steer` returns its reply.

## Common problems

`UZ-APPROVAL-002` means the gate is no longer open. It timed out, or someone decided it in the dashboard. List the gates again.

`UZ-APPROVAL-006` means someone decided this gate first. Run `agentsfleet approvals show <GATE_ID>` to read the outcome and who recorded it.

`UZ-GRANT-001` means the fleet holds no approved grant for the service it tried to mint against. No token is issued and the run makes no call to the provider. Check what the fleet holds with `agentsfleet grant list --fleet <FLEET_ID>`.

`UZ-REPAIR-010` and `UZ-REPAIR-011` are retired and no longer returned. Both described a per-event repository-write gate that is no longer raised. A run that cannot write now fails with `UZ-GRANT-001` instead.

## Remove or undo

A gate is decided once, and neither answer can be changed on the gate itself. Denying one ends that run without the access it asked for. What an approval created is a separate object, and an integration grant can be revoked.

An `integration_grant` decision does not expire. Its blast radius says so —
`every credential this fleet mints for <service>, until a person revokes the grant` — so approving one is a standing permission, not a single answer. Revoke
it with `agentsfleet grant delete <GRANT_ID> --fleet <FLEET_ID>`; list what a
fleet holds with `agentsfleet grant list --fleet <FLEET_ID>`.

Two different scopes, and picking the wrong one costs more than you meant.

To change which repositories a fleet may reach, or to drop it to read-only,
edit `repositories:` or `repository_access` in `TRIGGER.md` and push the bundle
with `agentsfleet fleet update`. The next minted token is scoped to what the
fleet now declares. The grant is untouched and the fleet keeps running.

To stop a fleet reaching the service entirely, delete its grant. A grant covers
one fleet and one service, never one repository, so deleting it halts every
repository that fleet reaches through that service.

The next event is refused before the fleet contacts the provider. This is the
emergency stop, not a way to narrow reach.

Run `agentsfleet approvals list --fleet <FLEET_ID>` to see which kind you are
actually being asked about — the `KIND` column names it.
