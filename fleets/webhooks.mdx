## What this does

A webhook delivery wakes a fleet after the server verifies the request. A workspace GitHub App routes its deliveries to fleets subscribed to each repository.

## Before you begin

For a fleet webhook URL, save a workspace secret with the sender's signing value in the `webhook_secret` field. For Svix, store the full `whsec_` value there. Use **Secrets** or [the secrets command](/fleets/secrets).

A custom webhook source uses lowercase letters, digits, and hyphens. It must be unique within the fleet. The names `approval` and `github` are reserved.

Match the verifier to the sender's signature. Built-in sources `linear` and `slack` choose their own recipe.

| Verifier scheme | What the sender signs | Signature header |
|---|---|---|
| `body-hex-sha256` | The raw body, with a `sha256=` prefix before the hex digest | Specify the provider header |
| `body-hex` | The raw body, with a bare hex digest | Specify the provider header |
| `body-base64-sha256` | The raw body, with a padded base64 digest | Specify the provider header |
| `slack-v0` | Slack's version and timestamp scheme | Slack's fixed headers |
| `svix-v1` | The Svix identifier and timestamp | Svix's fixed headers |

The body recipes use SHA-256 and a hash-based message authentication code (HMAC). A custom header is 1 to 128 characters and contains no spaces.

## Steps

### A connected GitHub App

1. Open **Connected apps** and connect GitHub to the workspace. Allow the App to see the repositories you need.
2. Ask the fleet to add a GitHub event trigger for those repositories. Name the event types you want, such as `pull_request`.
3. Check the trigger under **Wakes on**. Approve a scoped GitHub request in chat if the fleet needs to make calls to GitHub.

The App already sends deliveries to agentsfleet. The repository list on the trigger limits where the fleet receives events. It can receive `pull_request` events and failed `workflow_run` events.

The server ignores deliveries from repair branches.

### A fleet URL

1. Ask the fleet to add a webhook with a source name, signing secret name, and verifier. Include any event filters you want.
2. Copy the URL listed under **Wakes on**, or list the triggers in your terminal.

   ```bash
   agentsfleet fleet triggers list <FLEET_ID>
   ```

   ```text
   <varies>
   ```

   Select the entry with the matching source. Its URL ends in `/v1/webhooks/<FLEET_ID>/<SOURCE>`.

3. Register the URL and signing secret with the sender.

For example, ask the fleet to add an `acme` webhook using secret `acme-signing`, the `body-hex-sha256` scheme, and header `x-acme-signature`.

The stored secret name is the trigger's `secret_name`.

## Verify it works

Check that the fleet received a turn in its chat. Use the fleet identifier from `agentsfleet fleet list` to check in the terminal.

```bash
agentsfleet fleet turns <FLEET_ID> --actor 'webhook:*' --since 1h
```

```text
<varies>
```

A newly accepted delivery returns HTTP `202`. A filtered or inactive delivery can return HTTP `200` without starting a turn.

## Common problems

| Error | Why it happened | Fix |
|---|---|---|
| `UZ-WH-001` | The webhook URL is wrong, or the fleet or trigger was removed. | Copy the current URL from its trigger. |
| `UZ-WH-010` | Signature verification failed. | Use the same signing secret and recipe on both sides. |
| `UZ-WH-011` | The signed timestamp differs by more than five minutes. | Correct the sender clock. |
| `UZ-WH-020` | The workspace has no usable signing credential. | Set `webhook_secret` in the workspace secret named by the trigger. |
| `UZ-WH-030` | The request exceeds the size limit. | Shorten the body to at most 1 MiB. |

For a rate-limited delivery, the sender should wait for the delay in the `Retry-After` response header before retrying.

## Remove or undo

Remove the provider registration, then remove the trigger under **Wakes on**. You can also run `agentsfleet fleet triggers delete <FLEET_ID> <TRIGGER_ID>`.
